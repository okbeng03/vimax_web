# 功能规格说明：调度模式与调度管理

**功能分支**: `002-schedule-mode`

**创建日期**: 2026-08-20

**状态**: Draft

**输入**: 用户描述："结合调度服务支持调度模式。调度服务通过 backend 调用，配置项配置调度服务地址（http://127.0.0.1:8001）。1. 项目详情：支持开启调度模式；调度模式下只有调度完成或取消调度才能切换到执行模式；增加日志监听任务监听 vimax_main 日志，获取 workflow_path(file_path)、workflow_name、output_ids、prompt_id、type(generation_type)，格式与 generation_result 一致，日志格式为 `[COMFYUI SCHEDULE]:: prompt_id: ..., type: ..., workflow_name: ..., workflow_path: ..., output_ids: ...` 和 `[COMFYUI SCHEDULE DETAIL]:: file_path: ...`；获取后调用 vimax_schedule 接口同步调度任务，首次项目调度任务同步新建项目；调度模式下产生调度任务则更新状态"调度中"；可取消调度任务；可置顶项目调度任务。2. 新增调度管理：调度项目列表（获取调度结果返回已完成任务列表，获取任务结果返回 comfyui output view，调用 comfyui view api 获取结果保存到项目目录并生成 generation_result；按优先级排序罗列任务数量；可置顶可取消）；项目调度任务列表（可取消调度任务）。"

## Clarifications

### Session 2026-08-20

- Q: 调度服务调用是否需要鉴权，采用何种方式？ → A: 调度服务提供 API_KEY，本地配置，调用时请求头携带 `X-API-Key`
- Q: 调度任务状态与结果的获取机制？ → A: 在调度管理页面点击"获取结果"按钮，调用调度服务 `/api/v1/results` 获取已完成结果列表，再逐个请求任务结果
- Q: 调度模式下生成任务的实际执行链路？ → A: 项目详情点击执行时本机 vimax_main 执行并输出 `[COMFYUI SCHEDULE` 格式化日志；web 监听日志识别信息后调用 vimax_schedule 同步；调度器记录任务并执行队列调用 comfyui 完成生成；web 最终主动同步调度结果
- Q: 调度项目与本地项目的关联映射？ → A: 以调度服务项目 id 为准，调度服务项目保存 web 的项目 id 和 name；调度管理以透传调度服务 API 为主，让前端直接调用

## 用户场景与测试 *(必填)*

### 用户故事 1 — 开启调度模式并受约束地切换执行模式 (优先级: P1)

作为一名创作者，我希望在项目详情中随时开启或关闭调度模式。开启调度模式后，项目通过调度服务进行任务分发与排队执行；在调度模式处于"进行中"时，系统禁止我将项目切换回执行模式，直到调度任务全部完成或我主动取消调度，以确保同一项目的执行方式不会在中途混用、避免产生冲突的生成结果。

**优先级理由**: 调度模式是本功能的核心入口。没有可靠的模式开关和切换约束，后续的调度任务同步、结果回传都无从谈起，且模式混用会导致同一项目产生双份不可控的生成结果。

**独立测试**: 可通过在项目详情开启/关闭调度模式、在调度进行中尝试切换执行模式并观察被拒绝、在调度完成或取消后成功切换来完整验证，交付"可控的调度模式开关"这一核心价值。

**验收场景**:

1. **Given** 用户在项目详情页，**When** 用户点击"开启调度模式"，**Then** 项目进入调度模式，界面明确显示当前处于调度模式，且后端已与调度服务建立关联。
2. **Given** 项目处于调度模式且存在尚未结束的调度任务，**When** 用户尝试切换到执行模式，**Then** 系统拒绝切换并提示"需等待调度完成或先取消调度"。
3. **Given** 项目的调度任务已全部完成，**When** 用户尝试切换到执行模式，**Then** 切换成功，项目回到可执行生成的状态。
4. **Given** 项目处于调度模式且存在尚未结束的调度任务，**When** 用户先取消全部调度任务再切换执行模式，**Then** 系统允许切换。
5. **Given** 项目未开启过调度模式，**When** 用户查看项目详情，**Then** 界面提供清晰的调度模式开关，关闭状态下不影响原有执行模式的任何功能。

---

### 用户故事 2 — 调度模式下自动同步调度任务并实时反馈状态 (优先级: P1)

作为一名创作者，我希望在调度模式下启动生成后，系统能自动监听 ViMax 的运行日志，识别出调度相关的生成事件（工作流、输出节点等），并自动将每一次调度事件同步到调度服务（同一项目首次同步时自动在调度服务中建立对应项目）。同时，只要产生了调度任务，项目状态就显示为"调度中"，以便我无需手动登记就能让调度服务感知全部生成任务，并实时掌握项目的调度状态。

**优先级理由**: 日志监听与任务同步是"调度模式"的核心能力——它让调度服务自动获得任务，是调度执行、结果回传整条链路的数据来源，缺失则调度模式无法工作。

**独立测试**: 可通过在调度模式下启动一次生成、观察日志中出现的调度事件被解析并在调度服务中同步出任务、以及项目状态变为"调度中"来完整验证。

**验收场景**:

1. **Given** 项目处于调度模式且用户启动了生成，**When** ViMax 运行日志中出现 `[COMFYUI SCHEDULE]::` 格式的调度记录，**Then** 系统解析出其中的 prompt_id、type、workflow_name、workflow_path、output_ids，并与紧随其后的 `[COMFYUI SCHEDULE DETAIL]::` 记录中的 file_path 关联，形成与 generation_result 同构的一条调度事件。
2. **Given** 该项目的调度任务在调度服务中尚不存在，**When** 首次产生调度事件，**Then** 系统自动在调度服务中同步创建对应项目并登记该调度任务。
3. **Given** 项目在调度服务中已存在，**When** 后续产生新的调度事件，**Then** 系统将任务同步到已有项目下，不重复创建项目。
4. **Given** 调度模式下产生了至少一个调度任务，**When** 用户查看项目详情或项目列表，**Then** 项目状态显示为"调度中"，且能看到任务数量。
5. **Given** 调度任务状态发生变化（完成或取消），**When** 用户刷新项目状态，**Then** "调度中"状态相应更新，不再显示未结束的调度任务。

### 用户故事 3 — 调度管理：浏览调度项目并按优先级管理 (优先级: P1)

作为一名创作者，我希望有一个独立的"调度管理"入口，按优先级顺序浏览所有调度项目及其任务数量，并能对项目执行置顶（提升优先级）和取消操作，以便我能掌握全局调度队列、优先推进重要项目并随时终止不需要的调度。

**优先级理由**: 调度管理是本功能的第二个核心价值——它让用户能俯瞰全局调度队列并施加控制。多项目并发调度时，没有优先级管理和取消能力会导致队列失控。

**独立测试**: 可通过打开调度管理页、查看按优先级排序的调度项目列表与任务数量、置顶某个项目后观察其排序变化、取消某个项目并观察其状态变化来完整验证。

**验收场景**:

1. **Given** 调度服务中存在多个调度项目，**When** 用户打开调度管理页，**Then** 看到按优先级从高到低排序的调度项目列表，每个项目展示任务数量。
2. **Given** 用户希望某个低优先级项目优先执行，**When** 用户对该项目执行"置顶"，**Then** 该项目在列表中排到最前，且该设置对调度服务生效。
3. **Given** 用户不再需要某个项目继续调度，**When** 用户对该项目执行"取消"，**Then** 项目停止继续调度，列表状态同步更新。
4. **Given** 某个调度项目包含多个任务，**When** 用户展开查看该项目，**Then** 可以看到该项目下的调度任务列表，并可对单个任务执行取消。

### 用户故事 4 — 获取调度结果并自动回传为生成结果 (优先级: P1)

作为一名创作者，我希望在调度管理中查看已完成调度任务的结果，系统能自动获取调度服务中已完成（成功或失败）的任务列表，通过任务结果拉取 ComfyUI 的输出预览（view），并把结果文件保存到本地项目目录，生成一条与现有 ComfyUI 生成结果一致的记录（generation_result），以便我能像普通生成一样浏览、确认和重试这些由调度模式产出的结果。

**优先级理由**: 结果回传让调度模式的产出与主平台的生成结果体系无缝融合，是调度链路闭环的最后一步。若结果无法回传，调度模式产出将无法被创作流程继续使用。

**独立测试**: 可通过触发获取调度结果、看到已完成任务列表（含成功与失败）、打开某任务的输出预览、确认结果文件已保存到项目目录且生成了一条 generation_result 来完整验证。

**验收场景**:

1. **Given** 调度服务中存在已完成的调度任务，**When** 用户触发"获取调度结果"，**Then** 系统返回已完成任务列表，并区分标注成功与失败。
2. **Given** 某调度任务执行成功，**When** 用户查看其任务结果，**Then** 系统展示该任务的 ComfyUI 输出预览（view）。
3. **Given** 任务结果可获取，**When** 系统回传该结果，**Then** 输出文件被保存到该项目目录下，并在项目中生成一条 generation_result 记录，其字段（file_path、workflow_name、prompt_id、generation_type 等）与既有生成结果一致。
4. **Given** 某调度任务执行失败，**When** 用户查看结果列表，**Then** 失败任务被明确标记并展示失败原因，且不会生成伪造的成功结果记录。
5. **Given** 结果已回传并生成 generation_result，**When** 用户在项目详情的结果页浏览，**Then** 该记录与手动/执行模式生成的结果无差异，可正常预览、确认与重试。

---

### 用户故事 5 — 调度任务粒度的取消操作 (优先级: P2)

作为一名创作者，我希望在"项目调度任务列表"中针对单个调度任务执行取消，以便当某个具体任务不再需要执行时（例如发现配置错误），我可以终止它而不影响项目中的其他调度任务。

**优先级理由**: 任务粒度的精确控制避免"一取消全取消"的粗放操作，减少资源浪费。它依赖于调度项目列表能力，因此优先级次之。

**独立测试**: 可通过打开某调度项目的任务列表、取消其中一个任务、确认该任务状态变为已取消而其余任务不受影响来完整验证。

**验收场景**:

1. **Given** 某调度项目下有多个未完成任务，**When** 用户取消其中一个任务，**Then** 该任务在调度服务中被取消，状态更新为已取消，其余任务保持原状态继续调度。
2. **Given** 某任务已处于完成或失败状态，**When** 用户尝试取消，**Then** 系统提示该任务不可取消或取消操作被忽略。

### 边界情况

- 调度服务不可用（网络不通或服务未启动）时，开启调度模式、同步任务、获取结果如何处理？——系统应给出明确可读的错误提示，允许用户重试；同步任务应有重试机制，避免一次失败即丢失调度事件。已解析但同步失败的调度事件应保留待重试。
- 日志中的 `[COMFYUI SCHEDULE]::` 记录缺少紧随其后的 `[COMFYUI SCHEDULE DETAIL]::` 记录（file_path 缺失）时如何处理？——该条调度事件标记为"file_path 待补"，不得生成不完整的 generation_result；待 DETAIL 记录到达后再补全。
- 同一项目在调度模式下被再次启动生成，产生新的调度事件时如何避免重复同步？——以 prompt_id 为唯一标识去重，已同步过的任务不得重复登记。
- 用户开启调度模式但从未启动生成（未产生任何调度事件）时，项目应处于什么状态？——处于"调度模式、空闲"状态，未结束任务数为 0，此时允许直接切换回执行模式。
- 取消调度与正在回传的结果冲突时如何处理？——任务取消后不再回传其结果；已在回传途中的结果按其实际完成情况处理，并记录操作日志。
- 置顶对已有排队顺序的影响？——置顶将项目提升到调度队列最高优先级位置；多个置顶项目之间按置顶先后排序。
- 调度模式下项目与全局"同一时间仅一个项目生成中"的既有限制如何兼容？——调度模式下的执行同样遵循全局并发限制，避免多个本地生成进程叠加。

## 需求 *(必填)*

### 功能需求

**调度服务配置**
- **FR-001**: 系统必须提供调度服务地址与 API_KEY 的配置项，由后端加载并生效，服务地址默认值为 `http://127.0.0.1:8001`。调度模式相关操作均调用该服务；调用时必须在请求头携带 `X-API-Key`（值为调度服务分配的 API_KEY）用于鉴权，未配置或鉴权失败时给出明确错误提示。

**调度模式开关与模式切换约束**
- **FR-002**: 系统必须在项目详情中提供"开启/关闭调度模式"的操作，开启后项目进入调度模式，并展示明确的调度模式标识。
- **FR-003**: 系统必须约束：项目处于调度模式且存在未结束的调度任务时，禁止切换到执行模式；仅当所有调度任务完成、或用户主动取消全部调度后，才允许切换回执行模式。被拒绝的切换必须给出明确原因提示。
- **FR-004**: 调度模式下，项目一旦产生调度任务，其状态必须更新为"调度中"；当调度任务全部结束（完成/取消/失败）时，状态随之恢复为非调度中状态。
- **FR-005**: 关闭调度模式前，若仍存在未结束的调度任务，系统必须要求用户先确认（确认后自动取消全部调度任务）或明确提示存在未完成任务，不得静默关闭。

**日志监听与调度事件解析**
- **FR-006**: 调度模式下，系统必须监听 ViMax（vimax_main）运行日志，识别 `[COMFYUI SCHEDULE]::` 前缀的调度记录，解析出 prompt_id、type（映射为 generation_type）、workflow_name、workflow_path、output_ids 字段。
- **FR-007**: 系统必须将 `[COMFYUI SCHEDULE]::` 记录与紧随其后出现的 `[COMFYUI SCHEDULE DETAIL]:: file_path: ...` 记录关联，合并得到 file_path，最终形成的调度事件字段结构必须与 generation_result 一致（file_path、workflow_name、prompt_id、generation_type、output_ids）。
- **FR-008**: 缺失 file_path（DETAIL 记录未到达）的调度事件必须被暂存等待补全，不得生成不完整的 generation_result。
- **FR-009**: 调度事件必须以 prompt_id 为唯一标识进行去重，重复出现的记录不得重复同步。

**调度任务同步**
- **FR-010**: 系统必须在解析出调度事件后，自动调用调度服务（vimax_schedule）同步该调度任务。完整执行链路为：调度模式下用户在项目详情点击执行 → 本机 vimax_main 照常发起执行并输出 `[COMFYUI SCHEDULE` 格式化日志 → web 监听日志识别调度信息并同步至调度服务 → 调度服务记录任务并通过其执行队列调用 ComfyUI 完成生成 → web 最终主动同步调度结果。
- **FR-011**: 项目首次同步调度任务时，系统必须自动在调度服务中同步创建对应项目；后续任务同步到该既有项目下，不重复创建。
- **FR-012**: 调度任务同步失败时，系统必须保留该事件并提供重试，不得静默丢弃；同步成功的任务必须能从本地状态确认。

**调度管理（新增入口）**
- **FR-013**: 系统必须提供独立的"调度管理"入口，展示调度项目列表。调度管理的项目/任务数据以调度服务项目 id 为准（调度服务侧保存有 web 的项目 id 与名称），后端主要透传调度服务的 API 供前端调用，不在本地维护独立映射表。
- **FR-014**: 调度项目列表必须按优先级从高到低排序，并罗列每个项目的调度任务数量（含未完成/完成/失败统计）。
- **FR-015**: 系统必须支持对调度项目执行"置顶"，将其提升到调度队列最高优先级。
- **FR-016**: 系统必须支持对调度项目执行"取消"，终止其后续调度。
- **FR-017**: 系统必须在调度管理页提供"获取结果"操作：点击后调用调度服务结果列表接口（`/api/v1/results`）获取该项目的已完成任务列表，并区分成功与失败。
- **FR-018**: 系统必须支持查看单个已完成任务的结果：获取结果列表后逐个请求各任务的结果接口，通过 ComfyUI 的 output view 能力展示输出预览。
- **FR-019**: 系统必须将成功任务的结果文件保存到该项目本地目录，并生成一条 generation_result 记录（字段与既有 ComfyUI 生成结果一致），使该结果可正常预览、确认与重试。
- **FR-020**: 失败任务必须标记失败状态并展示失败原因，不得生成伪造的成功结果。
- **FR-021**: 系统必须提供"项目调度任务列表"（单个调度项目下的任务明细），并支持对单个任务执行取消。
- **FR-022**: 已完成或已失败的任务不可被取消，系统必须给出相应提示。
- **FR-023**: 结果回传与任务取消必须遵循先后一致性：任务取消后不得再回传其结果。

**操作记录与审计**
- **FR-024**: 系统必须记录调度模式下的关键人工操作（开启/关闭调度模式、置顶、取消项目/任务、获取结果），纳入既有操作记录体系，可追溯。

### 关键实体

- **项目（Project）— 扩展**: 在既有项目实体上扩展调度相关属性：是否开启调度模式、当前调度状态（空闲/调度中）、未结束调度任务数。调度状态用于模式切换约束与"调度中"展示。
- **调度项目（Schedule Project）**: 调度服务侧的项目，以调度服务项目 id 为准，并保存 web 的项目 id 与名称用于关联。包含项目标识、名称、优先级、任务数量统计。首次同步任务时自动创建；调度管理通过透传调度服务 API 呈现，本地不维护独立映射表。
- **调度任务（Schedule Task）**: 调度服务中的一次生成任务，对应一条调度事件。包含 prompt_id、workflow_name、workflow_path（file_path）、output_ids、type（generation_type）、状态（排队中/执行中/成功/失败/已取消）、失败原因。以 prompt_id 唯一。
- **调度事件（Schedule Event）**: 从 ViMax 日志解析出的原始记录，包含 prompt_id、type、workflow_name、workflow_path、output_ids、file_path，结构对齐 generation_result。同步到调度服务后成为调度任务。
- **调度结果（Schedule Result）**: 已完成调度任务的产出，含 ComfyUI output view 信息与结果文件。回传到本地后保存到项目目录并落库为 generation_result。

## 成功标准 *(必填)*

### 可衡量成果

- **SC-001**: 创作者能在 1 分钟内完成项目调度模式的开启，并立即看到明确的调度模式状态标识。
- **SC-002**: 调度模式下产生的调度事件，从日志出现到成功同步至调度服务，100% 在 30 秒内完成（服务可用时）。
- **SC-003**: 格式正确的调度日志记录 100% 被正确解析并去重同步，不产生重复任务；缺失 file_path 的记录 100% 被暂存补全而非生成不完整结果。
- **SC-004**: 模式切换约束 100% 生效：存在未结束调度任务时切换执行模式被拒绝；调度完成或取消后切换成功。
- **SC-005**: 调度管理页中，调度项目按优先级正确排序，任务数量展示准确，置顶操作在 2 秒内生效并反映到排序。
- **SC-006**: 成功调度任务的结果在触发"获取调度结果"后 3 分钟内完成回传，且生成的 generation_result 在项目结果页可见、可预览。
- **SC-007**: 失败调度任务 100% 被标记并展示失败原因，不生成伪造的成功结果。
- **SC-008**: 调度服务不可用时，用户在界面上 10 秒内看到明确错误提示，且已解析的调度事件不会丢失，恢复后可重试。

## 假设

- 调度服务（vimax_schedule）为独立部署的服务，提供项目管理、任务登记/同步、任务取消、优先级调整（置顶）、结果查询等能力。调度项目以调度服务项目 id 为准，调度服务侧保存 web 的项目 id 与名称；调度管理主要透传调度服务 API 供前端调用，本地不维护独立映射表。已完成结果列表通过 `/api/v1/results` 获取，结果明细（ComfyUI output view）需逐个请求任务结果接口获取。其余接口契约在规划阶段结合其 API 文档（http://127.0.0.1:8001/docs）确定，本规格不限定接口实现。
- 日志监听复用现有 ViMax 日志获取链路（stdout 临时文件 + 实时推送），在调度模式下额外解析 `[COMFYUI SCHEDULE]::` 与 `[COMFYUI SCHEDULE DETAIL]::` 两类记录；`[COMFYUI SCHEDULE]::` 行先出现，`[COMFYUI SCHEDULE DETAIL]::` 行紧随其后提供 file_path。
- 调度事件字段映射关系：日志中的 type → generation_type、workflow_path → file_path（最终以 DETAIL 行的 file_path 为准）、output_ids → 输出节点 ID 列表，整体结构与既有 generation_result 一致。
- 调度模式下，用户在项目详情点击执行后本机 vimax_main 照常发起执行并输出 `[COMFYUI SCHEDULE` 格式化日志；web 监听日志识别调度信息并调用 vimax_schedule 同步任务；调度服务负责记录任务并通过其执行队列调用 ComfyUI 完成生成；web 最终主动同步调度结果（通过 `/api/v1/results` 拉取已完成列表并逐个获取任务结果）。
- 结果回传通过 ComfyUI 的 view（output view）接口获取输出，结果文件保存到本地项目目录后按既有 generation_result 规则落库，复用既有的预览/确认/重试能力。
- "置顶"语义为将调度项目提升至调度队列最高优先级；多个置顶项目按置顶时间先后排序。取消语义为终止项目的后续调度及其中未完成任务。
- 调度模式下的生成执行遵循平台既有"全局同时仅一个项目生成中"的并发限制。
- 无调度任务（未产生调度事件）时，调度模式项目处于"调度模式-空闲"状态，允许直接切换回执行模式。
- 调度服务地址与 API_KEY 通过后端配置项提供，服务地址默认 `http://127.0.0.1:8001`，API_KEY 由调度服务分配。backend 调用调度服务时在请求头携带 `X-API-Key` 进行鉴权。
